Scans the repo at `/self-improve init` for structural patterns and proposes initial coupling rules.

## Input

You receive a recursive listing of the repo's directory tree (file paths only, generated by the calling command). You do not need to read file contents — structure alone drives this pass.

## Algorithm

1. **Group top-level directories by glob pattern.** Identify families of sibling directories that share a naming convention. Examples:
   - `packages/typescript/ai-*` (sibling provider/integration packages)
   - `examples/ts-*-chat` (sibling example apps)
   - `apps/*` (sibling deployable apps in a monorepo)
   - `services/*` (sibling backend services)
   Use the longest common prefix-plus-glob that captures 3 or more sibling directories. Skip groups with fewer than 3 siblings — too small to generalize.

2. **For each group with N ≥ 3 siblings:** list the relative file paths inside each sibling. Compute the **spine** — the set of file paths (relative to each sibling's root) that appear in all N siblings. Compute the **per-sibling unique** set — files present in some siblings but not others. The spine is the high-confidence required surface; unique files are noise.

3. **Compose a candidate coupling rule per group.** The rule has:
   - `trigger`: `"adding new directory matching <glob>"`.
   - `impacts`: one entry per spine file, with `kind: new-code-required`, `target` set to the path the new sibling would need at the same relative position, and `why` citing how many existing siblings have this file (e.g. "Present in 7 of 7 siblings: package.json, src/index.ts, tsconfig.json").

4. **Cross-directory impacts.** When a sibling family obviously requires registration outside its own tree (e.g. a new `examples/ts-<framework>-chat` should appear in a top-level `examples/README.md` or workspace config), include those external targets as additional impacts with `kind: new-code-required`. Identify these by looking for files at the repo root (or one level down) whose names suggest registries: `pnpm-workspace.yaml`, `nx.json`, `examples/README.md`, `tsconfig.references.json`, top-level `package.json`.

## Confidence scoring

For each candidate rule, assign confidence:

- **high** — spine ≥ 5 files AND all siblings share 100% of the spine.
- **medium** — spine ≥ 3 files OR one sibling deviates on a non-critical file.
- **low** — spine < 3 files, or the sibling group is heterogeneous and the spine is essentially just `package.json`.

Drop rules with confidence below `low`.

## Output

Output a JSON array ranked from highest to lowest confidence:

```json
[
  {
    "id": "<kebab-case-id>",
    "confidence": "high",
    "example_sibling": "<path to one existing sibling that the rule was derived from>",
    "rule": {
      "id": "<same kebab-case-id>",
      "trigger": "adding new directory matching <glob>",
      "impacts": [
        {
          "target": "<relative-path-in-new-sibling>",
          "kind": "new-code-required",
          "why": "Present in <N> of <N> existing siblings (<example-sibling>)."
        }
      ]
    }
  }
]
```

The `rule` sub-object must validate against `templates/coupling.schema.json`. The user accepts or rejects each rule interactively; accepted rules are appended to `.agent/self-learning/coupling.json`.

Output only the JSON array. No prose, no code fences.
